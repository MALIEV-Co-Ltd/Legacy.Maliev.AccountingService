# Invoice-only Notification V2 consumer candidate

Status: source candidate, not runtime acceptance. This implements the owner-approved modern Accounting decisions23/49/50; it does not reopen or relabel the original source baseline or archived graph. Notification producer contract remains2a844283b930321bc06da692282f568fbd921874; deployment and both consumer/producer feature activation remain off.

The actual invoice controller captures the issuer from the independently verified short-lived employee delegation. Enabled invoice email requires that exact retained issuer/employee/service/quotation/operation admission before journal replay or financial effects. Old admission rows keep a null issuer and receive no invented authority. The additive public EmailState=3 means ProviderAccepted; existing0/1/2 retain their values, and legacy receipt notification remains V1.

The source migration adds nullable OriginIssuer and FinancialResultJson without defaults or backfill. FinancialResultJson records only this workflow's actual invoice/file completion, with NotRequested email state and no provider identifier, before V2 starts. An uncertain admission can access authenticated read-only reconciliation. Provider acceptance alone cannot establish financial completion. Migration application is not authorized by source acceptance.

One invoice-purpose first writer retains the original distinct Intent UUID, complete actor/workflow/sender tuple and keyed payload commitment. Prepared→AdmissionIssued and Admitted→ExecutionIssued use versioned durable CAS. Only acknowledged commit and transaction/context disposal produce sealed, single-use permits; public constructors and snapshot-to-permit factories do not exist. Each permit binds the exact payload digest and is consumed before HTTP. Ambiguous local commit or response loss leads to GET reconciliation, never reissue, a replacement Intent, changed payload or V1 fallback.

The immutable owned payload deep-copies arrays and attachment bytes. Both digest and execute JSON use that same snapshot. The digest preserves strict UTF8, null-versus-empty arrays, ordered recipients/attachments and raw attachment bytes using notification-payload-v1 framing. No HMAC secret crosses the wire; Accounting retains its own independent runtime keyring. Keys must remain available for retained intents, including terminal replay.

Wire requests and receipts are exact camel-case. Receipts require all identity/state/version/timestamps, forbid duplicate/unknown properties and null optional providerMessageId, require explicit timezone offsets and exact microsecond timestamps, and enforce producer status/state consistency. ProviderAccepted is not recipient delivery. Missing, denied, unavailable or malformed GET is unresolved. The client has no POST resilience retry and disables redirects in its registered transport.

Recovery reads the original financial evidence and same retained intent. It performs no financial creation/completion, PDF rendering, file upload, PUT or POST. Terminal completed3 replay checks the retained provider receipt HMAC against the public result without Notification HTTP. A disabled consumer with any retained V2 fence cannot fall back to legacy invoice sends.

Validation is GitHub-hosted only. Candidate tests cover PostgreSQL first-writer/CAS/commit-disposal faults, actor issuer retention, financial write-once authority, owned payload mutation/framing, strict receipts, controlled transport loss and actual Accounting controller JWT/live-IAM recovery. Controlled Notification transports are not real producer joins or real AuthService exchange proof. The Files owner separately owns the real pinned Notification producer join and counterpart Intranet owns truthful EN/TH value3 handling. Full/focused suites, raw generated-inclusive coverage, formatting/audit/scans and the explicitly versioned17-case graph remain required before acceptance.
